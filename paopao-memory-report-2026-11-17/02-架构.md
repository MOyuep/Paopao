# 02 · 架构

> 路径一律用占位符：`<PROJECT_ROOT>` = 项目根目录，`<STATE>` = 运行时状态目录。

---

## 一、模块地图

```
<PROJECT_ROOT>/src/
│
├─ 记忆层核心 ────────────────────────────────────────────────
│  memory-pipeline.js    写入唯一入口 writeMemory()。五阶段流水线。
│  memory-schema.js      类型定义 + 归一化 + 校验 + deriveFields()（字段补齐唯一处）
│  memory-store.js       分片文件读写（IO）
│  memory-merge.js       合并 / 冲突消解 / 证据加权裁决
│  memory-index.js       统一索引（长期记忆 + 图片摘要 + 会话话题 → 一个可搜索数组）
│  memory-retrieve.js    检索唯一入口 retrieve()。RRF + 三因子平手裁决
│  memory-embed.js       向量封装 + 内容键缓存（桥接与工具共用）
│  memory-write.js       写入闸门 sanitizeMemoryText()（规范化 + 基础过滤）
│  correction.js         极性与纠错意图识别
│
├─ 稳定性 ───────────────────────────────────────────────────
│  error-classify.js     错误分类（中毒 / 额度）+ 上报去重
│  wake-state.js         沉睡状态机（清醒 / 观察中 / 沉睡）
│
├─ 编排层 ───────────────────────────────────────────────────
│  bridge.js             主进程：QQ 事件循环、会话、注入、自动沉淀
│  mcp-snowluma-safe.js  MCP 工具层（对外暴露 recall / remember / forget / restore / pin 等）
│
└─ 测试与评估 ───────────────────────────────────────────────
   test-memory-contract.mjs          201 项
   test-wake-state-contract.mjs       53 项
   test-error-classify-contract.mjs   42 项
   eval-retrieval.mjs                26 条 golden query 的检索评估
   eval-fusion.mjs                   8 种融合策略对比（调参用）
```

**为什么这么拆**：早期单文件上万行，任何逻辑只能"改了重启看效果"。拆出来后每个模块都能脱离主进程单独测试——296 项断言不需要起进程、不需要连模型。

## 二、写入链路

```
调用方（四个入口）
  │  · 自动提取（定时从对话提炼）
  │  · 工具主动记
  │  · 人工确认待确认记忆
  │  · 纠正
  ▼
writeMemory(candidate, { items, enrich })
  │
  ├─ stage 1  sanitize ──────────── 规范化正文、拒空、拒太长
  │             subject 归一（禁「老板/对方/用户」，统一为「他」）
  │
  ├─ stage 2  metaGate ──────────── 词表级元信息拦截（快、免费）
  │             判据：系统名词 AND 验证措辞
  │
  ├─ stage 3  enrich ────────────── 【可注入，失败跳过】
  │             一次模型调用同时产出：
  │               category   A=关于某人 / B=关于系统维修
  │               polarity   positive / negative
  │               importance 1~10
  │
  ├─ stage 4  derive ────────────── deriveFields()：补齐全部字段（唯一一处）
  │             speaker   candidate > 推断（insight→self，其余→owner）
  │             basis     candidate > 推断（insight→inferred，其余→stated）
  │             importance candidate > enrich > kind 兜底
  │             polarity  candidate > enrich > 不写（留给读时兜底）
  │             id        没有就生成
  │             status / createdAt / updatedAt
  │
  └─ stage 5  consolidate ───────── upsertMemory()
                 先找最相似的候选（同 kind、同 user）
                 再判是否矛盾（极性闸门 + 语义判据）
                 ├ 矛盾 → 按证据强度裁决（谁的原话更可信）
                 └ 不矛盾 → 合并（只在"新文包含旧文"时替换正文）
  ▼
返回 { action: ADD | UPDATE | CONFLICT | REJECT }
  │
  └─ 调用方决定后续（日志 / 回复用户 / 落盘）

落盘：调用方统一 saveAll()
```

### 为什么"返回动作"而不是"顺手做掉"

调用方需要知道发生了什么才能正确回复用户（"已记住" / "已更新" / "与旧条矛盾" / "不入库：原因"）。
如果写成"函数内部默默处理"，调用方只能猜。

## 三、检索链路

```
查询
  ▼
buildPool()  ── 按用户/群/类型过滤 + 可选的"只看归档"
  ▼
┌──────────────── 两路召回 ────────────────┐
│                                           │
│  词面：BM25（分词见下）                     │
│  语义：向量余弦（内容键缓存，服务挂了跳过）    │
│                                           │
└───────────────────┬───────────────────────┘
                    ▼
            RRF 融合（rank-based，避免不同量纲直接相加）
                    ▼
          scoreWithTiebreak()
            主键 = round(相关度, 1e-4)
            次键 = 重要性 × 新鲜度 × 置顶 × 1e-5
                    │
      相关度永远压过因子；只有完全平手才看因子
                    ▼
              排序 → 分页 → 返回
```

### 分词（中文的关键）

每条内容切成：**单汉字 + 双字词 + 拉丁词**。

- 单汉字**保留为检索词**：否则「茶」这类单字查询会漏（实测修复前搜「茶」0 条，修复后 12 条）。
- 但单汉字**不计入文档长度**：否则中文天然字数多会把 BM25 分数压低。
- 停用词单独一张表。

### 三因子

| 因子 | 公式 | 范围 | 作用 |
|---|---|---|---|
| 重要性 | `0.6 + 0.08 × min(10, imp)` | 0.6 ~ 1.4 | 约定 > 偏好 > 事实 > 判断 |
| 新鲜度 | 30 天内 = 1；之后线性衰减，130 天触底 | 0.45 ~ 1 | 越新越优先 |
| 置顶 | 置顶 × 1.3 | 1 ~ 1.3 | 人工指定优先 |

## 四、数据模型

一条记忆的字段：

```
id           唯一句柄（删除/恢复/置顶都按它操作）
content      正文（主语统一第三人称「他」）
kind         fact / preference / promise / insight / lore / event / identity / weekly
speaker      owner（他说的） / self（我说的/我推的）
basis        stated（他原话） / inferred（我推断的）
polarity     positive / negative   ← 慢字段，未标注则读时用词表兜底
importance   1~10
status       live / invalid（手动作废） / superseded（被更强证据顶掉）
tags         标签数组
userId / scope / groupId   作用域
source       写入路径（auto-extract / qq_remember / correction / reflect / legacy）
beliefFrom   开始相信的时间
beliefTo     不再相信的时间（空 = 仍有效）
createdAt / updatedAt

审计字段（只在退役时写）
invalidReason / invalidatedBy
supersededBy / contentSupersededFrom
restoreNote / restoreAt
pinned / pinnedAt
```

### 三个作用域

```
shared    所有人可见
group     某个群可见
private   某个用户可见（默认）
```

**默认 private** 是刻意的——记忆里大量内容只该给当事人看。

## 五、存储布局

```
<STATE>/
  global-memory.json          长期记忆（一个数组）
  users/<id>.json             按用户分片
  image-memos.json            看过的图的文字摘要
  <会话状态>.json              会话/话题/唤醒配置
  backups/<tag>-<时间>/        每次批量改动前的快照（可回滚）
  memory-pending.json         待确认记忆队列
```

**批量改数据一律先备份再改**，备份目录名带改动标签和时间戳。

## 六、关键不变量（由测试保证）

```
1.  insight + 来源=反思  →  speaker=self 且 basis=inferred
2.  speaker=owner        →  basis=stated
3.  有效条目里不许出现以「老板」「用户」开头的正文
4.  有效条目里不许有系统元信息（promise 类型豁免）
5.  有效条目不带 beliefTo；归档条目都带
6.  beliefTo 不得早于 beliefFrom
7.  所有条目都有 id
8.  没有 polarity 字段时回退词面判断
9.  否定词表只有一个定义处
10. 不许绕过 writeMemory 直调底层 upsert
11. 排序方向：越新越高、越重要越高、置顶更高
12. 因子不能推翻明显的相关度差
```

## 七、一次查询的完整例子

> 举例用**中性合成场景**，不是真实记忆内容。

```
输入：查询「那个人平时用什么工具」
  ↓
过滤：只看该用户可见的有效记忆 → 151 条
  ↓
词面：BM25 打分 → 排名（这条查询与原文无共同词，正确答案排第 4）
语义：向量余弦 → 排名（正确答案排第 1）
  ↓
RRF 融合：正确答案在语义排 1、词面排 4 → 融合后进前 3
  ↓
三因子：它是普通事实（importance 5）、较旧（freshness 0.9）→ 微调
  ↓
返回：正确答案命中
```

对比：纯词面会把这条查询排到第 4（miss top3），**融合后进 top3**。这就是向量那套的价值。
