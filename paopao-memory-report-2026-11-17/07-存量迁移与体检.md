# 07 · 存量迁移与体检

> 这一章记一个**一夜内复发 4 次**的问题，以及最后落成的防复发机制。
> 它比任何单个功能都重要：**靠人记的教训必然再犯，只有做成启动哨兵才可靠。**

---

## 一、同一个坑，四次

| 次 | 字段 | 事故 |
|---|---|---|
| 1 | `polarity` | 只接一个写入入口，覆盖率卡 149/150 |
| 2 | `beliefFrom/To` | 改名后要迁移 199 条 |
| 3 | `id` | 重构时丢了，新条目没有 id（而删除/恢复/置顶都按 id 操作） |
| 4 | `importance` | 改成按 kind 算，但 **92% 存量仍是旧硬编码 5**，检索评分里因子恒等于 1.0 |

**根因**：`writeMemory → deriveFields` 这条单一写入入口只保护**新数据**。存量数据不在任何写路径上、没有任何机制碰它、也不会报错——于是「修好的功能在旧数据上还是死的」。

## 二、为什么架构改了还复发

因为「单一入口」和「存量迁移」是**两件不同的事**：

```
单一写入入口  →  保证「以后新写的」按新规则生成
存量迁移      →  修正「已经写进去的」旧数据
```

前者的保证再强，也管不到后者。一夜四次，就是每次只改了前者、忘了后者。

## 三、落成的机制

### 1. 回填

`importance` 144 条回填，分布从 `{5:142}` 变成 `{3:35, 4:5, 5:6, 6:45, 7:5, 8:31, 9:28}`——7 种取值、不再 92% 挤在一个值上。

### 2. 启动哨兵（关键）

检测逻辑抽成 `memory-audit.js`，**桥接每次启动自动跑**：

```
[memory] 存量体检通过：182 条有效 / 55 条沉底，无异常
```

不靠人记得跑。有问题每次启动都会喊。

### 3. 三条迁移铁律

1. 改字段生成逻辑/默认值 → 改前备份 → 改后跑体检 → 写迁移
2. 判据：**单一取值占比 >70% = 疑似未回填**（`polarity` 天然偏斜，只查 100%）
3. 迁移脚本**只改目标字段，绝不碰 `updatedAt`**（那是检索的新鲜度基准，改了等于抹平新鲜度信号）

---

## 四、两次自己的次生事故（已修）

| 事故 | 后果 | 教训 |
|---|---|---|
| 回填脚本顺手改了 `updatedAt` | 新鲜度信号被抹平，检索指标掉 | 迁移只改目标字段 |
| importance 进相关度排序 | 实测拉低 hit@1（18→17） | importance 是「谁进上下文预算」的判据，不是相关性 |

## 五、一个没解决的（记着）

检索评估数字会随记忆条数变化——151 条时 19/25，加 4 条新记忆变 18/25。**跨数据状态不能直接比数字**。要真正追踪回归，得冻结一份评估快照，这个还没做。
